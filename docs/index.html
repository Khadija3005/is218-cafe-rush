01 / Research question

How can a small café game save trustworthy, private scores?

Audience: college students wanting a quick casual game, and classmates reviewing the design. The question is how to combine playful drink-making with server-owned rules, persistent results and private accounts.

Finished promise: register → log in → complete a five-order round → save the verified score → view private history/best score → update display name/password → log out.

Assumption: assembling drinks will be enjoyable between classes. This has not been tested with players.

Interpretation: Café Rush offers a more playful project while keeping a small account-to-saved-result workflow. This is a preference, not evidence of player demand.

Rules for the first version

The server chooses five orders from espresso, latte and mocha. The player selects ingredients and submits each drink once. A correct recipe earns 20 points; an incorrect recipe earns zero and advances. Maximum score: 100. Timing is an experiment. Multiplayer, chat, payments and café-building are outside scope.

Framework comparison

Flask + SQLite

Fact: Flask's tutorial includes registration, login and user-owned posts [1].

Interpretation: a small route/service structure should help explain ownership and score validation. Security decisions still need explicit implementation.

Django + SQLite

Fact: Django provides accounts, permissions, hashing and sessions [4].

Interpretation: useful built-in structure, with more framework conventions to learn. Per-round ownership still needs explicit rules.

Choice: Python, Flask, Jinja/HTML/CSS, small JavaScript interactions, SQLite and pytest. This is not proof Flask is easier. Revisit after implementation checks or course constraints.

Storage comparison: browser-only storage would avoid a database server but would not by itself enforce server-side private accounts. SQLite supplies disk storage without a separate database process [3]. Choose it for the small planned game; hosting persistence and concurrent use remain to investigate.

03 / Primary evidence

Sources that shape the design

Original documentation opened with AI browsing assistance on November 12, 2026. These paraphrases support technical choices, not claims that the game is implemented or enjoyable.

  1. Flask tutorial: accounts and owner-managed records. Decision: adapt the ownership workflow to saved rounds.
  2. Flask: Blueprints and Views: related routes, validation, password hashes and SQL parameters. Decision: separate account/game routes and validate submitted drink choices on the server.
  3. Python sqlite3: disk storage, parameter binding and transaction handling. Decision: save final results transactionally and test persistence/repeated submissions.
  4. Django 5.2 Authentication: built-in accounts, sessions and permissions; generic auth does not supply object-level permissions. Decision: compare its convenience while keeping round ownership explicit.
  5. Flask Test Coverage: pytest, temporary databases and a request test client; coverage does not guarantee browser behavior. Decision: test scoring and account isolation, then have a classmate try the interaction.

Documentation versions are references, not installed dependencies. The research browser could not retrieve the full linked course instructions; additional constraints need a manual check against that page. The supplied assignment text guides this plan.

04 / Stories and architecture

Keep the fun in the browser and the rules on the server

LayerPlanned responsibility
BrowserDisplay order and ingredient controls; submit choices.
Flask routesAccount access, round actions, private dashboard and settings.
Game serviceAssign orders, validate recipes, advance state and compute score.
RepositoryParameterized SQL and transaction boundaries.
SQLiteUsers, rounds, attempts and final results.

Requests pass down these layers and return as rendered HTML. The server derives ownership from the signed-in user and computes scores from recorded actions; it must not trust a submitted total. Planned protections include replay prevention, password hashing, input validation and CSRF protection. None is implemented yet.

  1. As a player, register, log in and log out to keep results private.
  2. Choose ingredients to complete customer orders.
  3. Keep completed rounds after logout and restart.
  4. View only my score history and accurate best score.
  5. Update my display name and password while authenticated.

Planned checks: duplicate/bad credentials, all three recipes and invalid combinations, persistent records, duplicate final submission handling, two-account isolation and old/new password behavior.

The research site is static documentation on GitHub Pages. The future Flask game requires server hosting; this page does not run the game.

05 / Creative uncertainty

Exciting rush or unnecessary pressure?

A / Relaxed service

Five customer orders.
No countdown.
Correctness-only score.

B / Café rush

The same five orders.
A visible 90-second limit.
Correctness-only score.

Planned method: compare prototype rounds with and without the timer. Ask a classmate to identify an order, assemble a drink and describe pressure/confusion. Record errors, completion and comments. Alternate order for multiple reviewers.

Decision: keep the timer if it adds enjoyment without preventing understanding; otherwise revise or defer it. A single review gives exploratory feedback. If adopted, timing is enforced by the server.

Pattern experiment: compare recipe conditionals with a recipe lookup/strategy interface using the same correct/incorrect combination tests. Assess clarity and ease of adding a fourth recipe.

Both experiments planned — no results yet
