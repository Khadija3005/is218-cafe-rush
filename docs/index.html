01 / Research question

How can a small Python app save study records privately?

The audience is college students recording study time across courses, plus classmates reviewing the design. The research asks which approach supports account access, a useful interaction, persistent records, a private dashboard and account updates without expanding the project too far.

Promise: register and log in, enter a subject/minutes/date, save the session, view personal history and totals, update display name/password, and log out.

Assumption: students will find manual study logging useful. No user research has established this yet.

02 / Compare & choose

Rock-Paper-ScissorsPlay the computer; save outcomes and personal totals.Clear rules, but repeated rounds may lose interest.

Interpretation: the tracker fits a routine college task and gives a clear account-to-record workflow. This is a scope decision, not a claim that students prefer it.

Framework approaches

Flask + SQLite

Fact: the Flask tutorial demonstrates registration, login and owner-edited posts [1].

Interpretation: adapting this small record workflow should make the request/database boundaries easier to study. More security decisions remain the developer's responsibility.

Django + SQLite

Fact: Django supplies user accounts, permissions, password hashing and session authentication [4].

Interpretation: useful built-in structure, but more framework concepts to learn for this small plan. Record ownership still needs explicit design.

Choice: propose Flask, Jinja/HTML/CSS, SQLite and pytest. This is not a benchmark or proof Flask is easier. Revisit if implementation or course constraints favor another stack.

Storage approaches

Comparison: a browser-only record store would avoid a server database but would not by itself enforce server-side private accounts. SQLite provides disk storage without a separate database server [3]. Choose SQLite for the planned small application; deployment persistence and concurrent use still need investigation.

03 / Original sources

Evidence behind the choices

All sources below were opened and checked with AI browsing assistance on November 12, 2026. The student should open them during peer review too. Summaries are paraphrases; documentation evidence does not prove this application works.

  1. Flask tutorial — its introductory workflow includes accounts and users managing their own posts. Connection: adapt owner-linked records to study sessions.
  2. Flask: Blueprints and Views — groups related views and demonstrates server validation, password hashing and SQL parameters. Connection: separate authentication routes and validate session entry.
  3. Python: sqlite3 — describes a lightweight disk database and parameter binding; writes need transaction handling. Connection: persist sessions using parameters and verify saved data after restart.
  4. Django 5.2: Authentication — documents built-in accounts, permissions, hashing and sessions; object-level permissions are not supplied by the generic auth system. Connection: compare built-in authentication while keeping per-record ownership explicit.
  5. Flask: Test Coverage — demonstrates pytest, temporary databases and a request test client; coverage does not guarantee correct browser interaction. Connection: combine meaningful automated checks with actual peer/browser review.

Documentation versions are references, not installed dependencies. The linked full course instruction page could not be retrieved by the research browser; its additional requirements remain to be checked. This plan uses the assignment text supplied by the student.

04 / Design implications

Private by design, verified later

Browser — HTML/CSS forms and Jinja-rendered pages
Flask routes — authentication, sessions, dashboard and account requests
Services — validation, ownership rules and totals
Repository — parameterized SQL reads and writes
SQLite — users linked to their study sessions

Requests travel down these layers; responses return as rendered HTML. The server derives the owner from the signed-in account. Planned protections include password hashes, CSRF protection and server-side validation. This diagram describes intended architecture, not implemented protection.

Five short stories

  1. Create an account, log in and log out to keep records private.
  2. Enter a subject, positive whole-number minutes and date to record a session.
  3. Keep saved sessions after logging out and restarting the app.
  4. See only my history and accurate total minutes in a dashboard.
  5. Update my display name and password while authenticated.

Pattern experiment, planned: compare direct SQL in routes with a repository layer using identical validation, persistence and ownership checks. Assess explainability and complexity before choosing the final structure.
